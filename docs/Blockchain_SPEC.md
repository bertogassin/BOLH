# Minimal Blockchain Specification — BOLH (Guardio)

Project: BOLH

Примечание: блокчейн — встроенный компонент приложения BOLH. Названия блокчейна, монеты и приложения совпадают (BOLH). Спецификация описывает модуль блокчейна, который должен быть реализован как встраиваемая библиотека/сервис с чётким API для использования внутри мобильного/десктоп‑приложения.

Цель: реализовать безопасный, квантово‑устойчивый, приватный и высокопроизводительный рабочий блокчейн с общей эмиссией 10_000_000_000 монет и распределением вознаграждений 60/20/10/10.

Ключевые требования (резюме):
- Полная эмиссия: 10_000_000_000 монет.
- Распределение: 60% майнинг/активности (просмотр рекламы и пр.), 20% рефералы, 10% резерв, 10% реклама/маркетинг.
- Квантовая устойчивость: пост‑квантовые схемы для подписей и KEM.
- Высокая TPS: основной поток транзакций — максимально быстрый и дешёвый.
- Privacy by default (опционально скрытые транзакции) + функция селективного раскрытия (reveal) по ключу.
- Никаких NFT / токенов коллекционного характера — только рабочая валюта и сервисные платежи.

1) Архитектурный выбор (высокоуровнево)
- Гибридная архитектура: сочетание Epoch PoW (для эмиссии и распределения прав на вознаграждения) и BFT‑комитета для порядковой обработки транзакций и быстрой финализации.
  - Мотив: сохраняем "майнинг" (ваша 60% доля) как источника эмиссии и экономической безопасности, но устраняем узкое место PoW по TPS, делегируя быстрый порядок транзакций BFT комитетам, выбираемым по эпохам, где комитет определяется результатом PoW (miners elect committee).
  - Каждый майнинг‑эпоха (например, N блоков) выбирает валидаторов для следующей эпохи; эти валидаторы выполняют HotStuff/Tendermint‑style BFT для быстрого включения транзакций.

2) Консенсус и эмиссия
- PoW Epochs:
  - Майнеры соревнуются в PoW для генерации «эпоховых» блоков; один mined epoch блок формирует seed для выбора BFT‑комитета.
  - Эмиссия монет распределяется по эпохам: 60% от общей эмиссии распределяется через награды epoch miners + награды за приложение (просмотры рекламы и on‑chain активности) — детализацию можно уточнить по формуле вознаграждений.
- BFT Committee:
  - Комитет обеспечивает ordering и финализацию транзакций с низкой задержкой и высокой пропускной способностью (целевой TPS — десятки тысяч, реалистично достигается при использовании горизонтального масштабирования и sharding/partitioning на уровне приложения).

3) Формат блока и транзакции (минимум)
- EpochBlock (PoW): header {epoch_id, prev_epoch_hash, nonce, merkle_root_of_commitment, epoch_seed, miner_pubkey, reward_info, timestamp}
- BFTBlock: header {height, prev_hash, proposer, merkle_root, epoch_id, signature_set, timestamp}
- Transaction: {tx_type, inputs, outputs, amount, fee, nonce, pubkey, signature, optional_privacy_field}
  - Подпись и pubkey используют пост‑квантовую схему (см. раздел 5).
  - Для приватных транзакций: payload зашифрован симметричным ключом, разглашаемым через KEM (view‑key) или через zk/CT механизм.

4) Privacy и функция раскрытия
- Подход: транзакции по умолчанию прозрачные, есть опциональный приватный режим:
  - Приватные транзакции используют Confidential Transactions (amounts скрыты) + один из двух вариантов для отправителя/получателя: a) Stealth addresses + KEM (для адресов), b) zk‑proofs (опционально как Layer‑2/upgrade).
  - Для совместимости с квантовой устойчивостью использует KEM на Kyber и подписи на Dilithium (или SPHINCS+ опционально) для создания одноразовых ключей.
- Reveal: отправитель может создать «view key» (KEM output) и передать третьей стороне; также можно встроить escrow‑view механизм для регулируемых раскрытий (по желанию).

5) Пост‑квантовые криптографические выборы (рекомендации)
- Подписи: CRYSTALS‑Dilithium (баланс скорости/сигнатуры/безопасности). Для максимально высокой консервативности (но большие подписи) — SPHINCS+ как опция для критических сообщений.
- KEM / шифрование: CRYSTALS‑Kyber для защищённого обмена ключами.
- Хэш: BLAKE3 (быстрый, современных свойств) или SHA‑3 семейство если нужна строгая стандартность.
- Сочетание: использовать Dilithium для транзакционных подписей и Kyber для одноразовых обменов симм. ключами (view keys, stealth).

6) Производительность и масштабирование
- Горизонтальное масштабирование: sharding/partitioning логики учёта по приложениям (state sharding) и мульти‑комитеты.
- Optimistic batching: паковать транзакции в BFT блоки с высокой плотностью (меньше сериализационных накладных расходов).
- Сеть: libp2p‑style overlay (gossipsub) с опциональной работой через Tor/I2P для приватных узлов; основной быстрый p2p можно реализовать на Rust для производительности.

7) Безопасность и формальная верификация
- Критические модули (валидаторы, верификаторы подписи, проверка консенсуса) проектировать и писать на SPARK/Ada с целью формальной проверки, что исключит классы ошибок в логике начисления и проверок.
- Производительность и сеть — реализовать на Rust и связывать с проверяемыми SPARK компонентами через FFI.

8) Экономика токенов (примерная реализация распределения)
- Всего: 10_000_000_000 монет.
- 60% (6_000_000_000) — майнинг/активность: распределяется по эпохам и заданной кривой эмиссии (например, экспоненциальное снижение награды по эпохам или линейное распределение на X лет). Резервировать часть наград сразу для вознаграждения за просмотр рекламы (on‑chain receipts).
- 20% (2_000_000_000) — реферальная программа: фонды для поощрения приглашений — выделяются в многоконтурной программе.
- 10% (1_000_000_000) — резерв.
- 10% (1_000_000_000) — реклама/маркетинг.

9) API и интеграция
- Встраиваемая библиотека / Node API: реализовать модуль с чётким интерфейсом для приложения — предпочитаемые контракты:
  - Local library API (native bindings) для мобильного/десктоп клиента: функции создания/подписания транзакций, отправки в локальный узел, получения баланса и событий.
  - RPC API (REST/gRPC) для работы с удалёнными нодами/сервисами.
  - WebSocket for real‑time events.
- Light clients: SPV‑style proofs для подтверждения включения транзакции.

10) Roadmap (следующие шаги)
- A. Уточнить модель вознаграждений и кривую эмиссии (по годам/эпохам).
- B. Подготовить feasibility‑notes для реализации на SPARK/Ada и Rust (разделение обязанностей).
- C. Начать прототип ядра: спецификация форматов + малый reference node (на Rust) + формализация критических модулей в SPARK.

Вопросы/решения — кратко:
- NFT: исключены.
- Reveal: реализуемая опция через view‑keys/KEM.
- Полная PQ‑защищённость: подписи + KEM — покрыта; zk‑часть остаётся исследуемой (PQ zk ещё развиваются).
