# АБСОЛЮТНЫЙ ТЕХНИЧЕСКИЙ СТАНДАРТ ПРОЕКТА

**(Ultimate Quality & Performance Blueprint)**

---

## 0. ФИЛОСОФИЯ ПРОЕКТА (The Core)

1. **Превосходство как норма:** Мы не ищем компромиссов. Мы строим систему, которая будет эталоном надежности, скорости и чистоты кода. Экономия времени на этапе проектирования недопустима — это ведет к техническому долгу.
2. **Правильный инструмент для правильной задачи:** Используем языки по их назначению. Там, где нужна максимальная производительность и безопасность памяти — Rust. Для высоконагруженных сетевых взаимодействий и микросервисов — Go. Для клиентских интерфейсов (если потребуется) — Swift (iOS/macOS) или C++ (высокопроизводительные движки). Spark — только для распределенной обработки больших данных. Всё остальное (скриптинг, конфигурация) — на минимуме и только по необходимости.
3. **Интеллектуальная простота:** Следуем принципу KISS (Keep It Simple, Stupid), но не в ущерб гибкости. Сложность оправдана только там, где она неизбежна (например, сложные алгоритмы).

## 1. АРХИТЕКТУРНАЯ СТРАТЕГИЯ (Clean Modular Monolith First)

Мы начинаем с модульного монолита. Это позволяет избежать распределенного ада на старте, но сохраняет возможность легкого перехода к микросервисам в будущем.

### 1.1. Слои системы (Строгое разделение)

- **Domain (Ядро):** Чистая бизнес-логика, сущности, value objects, интерфейсы репозиториев. Никаких зависимостей от фреймворков или БД. Язык: Rust (из-за строгости типов и безопасности) или Go (для простоты).
- **Application (Use Cases):** Сценарии использования, оркестрация доменных объектов. Зависит только от Domain.
- **Infrastructure (Адаптеры):** Всё внешнее: БД (SQL/NoSQL драйверы), кэш (Redis), очереди (Kafka), файловое хранилище (S3), внешние API. Реализует интерфейсы, объявленные в Domain. Язык: Go (отлично подходит для написания адаптеров и работы с I/O) или Rust.
- **Presentation (Доставка):** API слой (REST/gRPC), обработчики запросов. Преобразует внешние DTO в внутренние модели. Язык: Go (идеален для API Gateway/веб-серверов).

### 1.2. Модульность (DDD Bounded Context)

- Каждый модуль (например, User, Payment, Notification) — это отдельная папка на верхнем уровне.
- Модуль содержит свои собственные слои (Domain, Application, Infrastructure), если это необходимо.
- Коммуникация между модулями — только через строго определенные интерфейсы (Application слои) или через асинхронные события (шина). **Прямой импорт Infrastructure одного модуля в Domain другого ЗАПРЕЩЕН.**

## 2. УПРАВЛЕНИЕ ФАЙЛАМИ И КОДОМ (The File Size Doctrine)

Основано на принципе: **Один файл — одна ответственность.** Размер — следствие логики, а не цель, но есть жесткие ориентиры.

### 2.1. Типы файлов и лимиты

| Тип | Строк | Примечание |
|-----|-------|------------|
| Доменная сущность / Value Object (Rust/Go) | 50–150 | Декомпозировать при превышении |
| Сценарий использования (Use Case) | 100–250 | Один файл = один сценарий; методы 5–20 строк |
| Репозиторий (Infrastructure) | 200–400 | Одна сущность на файл |
| Контроллер/Хендлер (Presentation, Go) | 150–300 | Только HTTP/gRPC: валидация, Use Case, ответ |
| Утилиты/Хелперы | 50–100 | Одна сложная функция = один файл |
| Сложный алгоритм / State Machine (Rust/C++) | до 800–1200 | Исключение; документировать и покрыть тестами |
| Конфигурация / Сгенерированный код | без ограничений | — |

### 2.2. Правила рефакторинга

- Если файл превышает лимит для своего типа — он **обязательно** разбивается.
- Длина метода более **40 строк** — запрещена. Метод должен делать что-то одно.
- Уровень вложенности (циклы/условия) — **не более 3-х**.

## 3. ТЕХНОЛОГИЧЕСКИЙ СТЕК (Языковой пуризм)

| Язык/технология | Где использовать | Почему |
|-----------------|------------------|--------|
| **Rust** | Domain (критическая логика), высоконагруженные сервисы, системные утилиты, обработка в реальном времени | Безопасность памяти без GC, производительность, система типов |
| **Go** | Application, Infrastructure (адаптеры), API (Presentation), I/O-bound микросервисы | Простота, горутины, стандартная библиотека для сетевых задач |
| **Swift** | Нативные клиенты Apple (iOS, macOS). Только UI | Экосистема Apple |
| **C++** | Абсолютный контроль над памятью и железом (движки, embedded, HFT). Изолированные модули | Производительность и контроль |
| **Apache Spark** | Отдельный кластер: пакетная обработка больших данных, ETL, аналитика. Не в основном потоке приложения | Масштабируемая распределенная обработка |

**Запрещено:** Использовать Python/JavaScript для core-логики (кроме прототипов или скриптов сборки).

## 4. ПРОИЗВОДИТЕЛЬНОСТЬ И ОПТИМИЗАЦИЯ

### 4.1. Бэкенд

- **Асинхронность везде:** Rust (Tokio), Go (горутины).
- **Кэширование:** Многоуровневое (in-memory в Rust/Go, Redis для общих данных).
- **БД:** Индексы под каждый частотный запрос. Запрещены N+1 (eager loading / dataloader).
- **Профилирование:** pprof (Go), perf/flamegraph (Rust) — часть CI для обнаружения регрессий.

### 4.2. Фронтенд (Swift/C++)

- 60 FPS гарантировано (120 FPS для ProMotion).
- Рендеринг через GPU (CoreAnimation/Metal, OpenGL/Vulkan).
- Ленивая загрузка ресурсов.

### 4.3. Сборка

- Минимальный размер бинарника: `opt-level = "z"` (Rust), `-ldflags="-s -w"` (Go).
- Tree shaking обязателен.

## 5. БЕЗОПАСНОСТЬ (Security by Design)

- **Валидация:** Все входные данные валидируются на уровне Presentation до Domain (validator в Rust, библиотеки валидации в Go).
- **Безопасность памяти:** Rust для критических частей исключает целые классы уязвимостей.
- **Секреты:** Никаких хардкодов. Только переменные окружения или зашифрованные хранилища (HashiCorp Vault).
- **Аудит зависимостей:** `cargo audit` (Rust) и `govulncheck` (Go) обязательны в CI.

## 6. ТЕСТИРОВАНИЕ И КАЧЕСТВО (Quality Gates)

### Пирамида тестирования

- **Unit (80%):** Доменная логика и use cases изолированно. Обязательны.
- **Интеграционные (15%):** Реальная БД, кэш, внешние API.
- **E2E (5%):** Критические сценарии (логин, платеж).

### Code Review

- Без аппрува минимум двух senior-разработчиков мерж в `main` запрещен.
- Проверяется код и архитектурное соответствие.

### Линтеры и форматтеры

- **Rust:** `rustfmt`, `clippy` (максимальная строгость).
- **Go:** `go fmt`, `go vet`, `staticcheck`.
- Запускаются на каждом коммите и в CI.

---

## 7. ПРОЦЕСС РАЗРАБОТКИ (The Golden Path)

1. **Проектирование:** Начинаем с документации. OpenAPI (Swagger) для API. ER-диаграммы для БД. C4 для архитектуры. Без утверждения архитектуры — код не пишется.
2. **Разработка:**
   - Ветвление: Trunk-based development или короткоживущие feature-ветки.
   - Коммиты: Conventional Commits.
3. **CI/CD:**
   - На каждый PR: линтер, компиляция, unit-тесты, интеграционные тесты, аудит безопасности.
   - На мерж в main: сборка staging, E2E тесты.
   - На релизный тег: сборка production, деплой.

---

## 8. ЗАПРЕЩЕНО (Do not cross)

- Глобальные переменные и синглтоны (кроме неизбежных случаев, например логгер).
- Циклические зависимости между пакетами/модулями.
- `nil`/`null` в доменной модели (использовать `Option<T>` в Rust).
- Бизнес-логика в хендлерах API или в SQL-запросах.
- Хардкод URL, портов, ключей.
- Закомментированный код — сразу удалять.
- Паника в библиотечном коде (Go) или `unwrap()` в production (Rust) — только после анализа или в тестах.

## Как использовать этот документ

1. **Инициируйте проект:** Репозиторий создан; этот файл — `ABSOLUTE_STANDARD.md` в корне.
2. **Настройте инструменты:** Линтеры и CI в соответствии с разделом 6.
3. **Ревью:** Код-ревью по этому документу. Нарушение философии = непринятие.
4. **Автоматизируйте:** Всё, что можно проверить скриптом (линтер, размер функций, тесты), — в CI. Человек проверяет только то, что не может машина (архитектура, читаемость, правильность бизнес-логики).
